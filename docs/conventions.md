# Conventions

The rules new code in this repository follows. Most are enforced by a test;
the test is named next to each rule. They follow the same standards as
[FloorSync](https://github.com/rileyrushton05/floorsync), where I owned the
database, data APIs and migrations, adapted to a smaller, serverless app.

## API

**Errors are RFC 9457 Problem Details.** Every error response, from domain
errors to unknown routes, validation failures and unexpected crashes, is
`application/problem+json`:

```json
{
  "type": "urn:meal-planner:problem:duplicate-name",
  "title": "Conflict",
  "status": 409,
  "detail": "A meal named 'Spaghetti Bolognese' already exists.",
  "instance": "/api/meals"
}
```

- `detail` is a sentence written for the person using the app; the
  frontend shows it as is. It never contains internals.
- `type` values are part of the contract. Add new ones; never rename one.
- Validation failures add `invalid_params`, one `{name, reason}` per field.
- Domain code raises exceptions from `app.exceptions`; `server/problems.py`
  is the one place that maps them to statuses and types.
- Unexpected exceptions become a generic 500 in `UnexpectedErrorMiddleware`,
  inside the request-context middleware so they keep their request id.

Tests: `tests/test_api_conventions.py` (problem details section).

**Request bodies are strict.** Every request model inherits `RequestSchema`
(`extra="forbid"`), so an unknown or misspelt field is a 422 rather than
silently dropped. Tests: strict requests section.

**The OpenAPI document is the contract.** `docs/openapi.json` is exported
from the app by `scripts/export_openapi.py`, and the frontend's types in
`web/src/api/schema.ts` are generated from it; `web/src/api/types.ts` only
gives them app-facing names. Both files are committed. A test fails if the
document is stale, and CI fails if the generated TypeScript is. Responses
inherit `ResponseSchema`, documented in serialization mode, so every field
the server always sends is required in the generated types; requests inherit
`RequestSchema`, where defaulted fields stay optional. Every error is
documented as `Problem` in `application/problem+json`.
Tests: `tests/test_openapi_contract.py`.

**HTTP semantics.** Creating returns `201 Created` with a `Location` header
that can be fetched. Deleting returns `204` with no body. Asking for a row
that does not exist, or that belongs to someone else, is a `404`.

**Who is asking.** Every data route takes `ServicesDep`, which requires a
signed-in user and hands back repositories bound to them; there is no other
way to get repositories, so a route cannot forget authentication. A route
that works signed in or out (only the auth routes) takes `OptionalUserDep`.
Without a session the answer is `401 not-signed-in`, which the frontend
answers by starting a guest session and retrying once. Writes from other
websites are refused app-wide by `server/origin.py`. Account rules (tokens,
expiry, rotation, password checks) live in `app/auth.py` and
`app/security.py`, never in route handlers.
Tests: `tests/test_auth.py` sweeps every route in the OpenAPI document for
a 401 without a session.

**Errors that keep their writes.** A request that raises rolls back, except
for errors marked `KeepsWrites` (a failed login, an "email taken" answer),
which commit first so the attempt they recorded is counted. Only for
errors raised before anything but that record is written;
`tests/test_transactions.py` lists the marked errors, so adding one is a
visible decision.

**Security events** go through `app.events.record`, which accepts only the
fields it lists. Passwords, tokens, emails and IP addresses are never
logged; where a line must say "the same caller as before", it carries a
prefix of the throttle's keyed hash.

## Observability

- Every response carries `X-Request-ID`, generated by the server. A
  client-supplied value is ignored.
- Every log line written while serving a request carries that id.
- Each request ends with one `http_request_completed` event: method, route
  template (`/api/meals/{meal_id}`, never the concrete path), status code
  and duration.
- Never logged: request or response bodies, query strings, cookies,
  authorization headers, passwords, tokens, database URLs.
- On Vercel logs are JSON lines; locally they are text. Override with
  `MEAL_PLANNER_LOG_FORMAT=json|text`. Run uvicorn with `--no-access-log` so
  requests are not logged twice.

Tests: request correlation and logging sections.

**Health checks.** `/health/live` touches nothing and says the process is up.
`/health/ready` checks the modeled tables and columns, plus the runtime
permissions on Postgres, and returns a 503 problem when the database is
unavailable or incompatible. Probes use SQLAlchemy expressions, fetch no
application rows, and never write data or advance sequences. Compatible
additive migrations remain ready; no migration-history access is required.
Postgres probe timeouts are transaction-local. The keep-warm workflow pings
`/health/ready`. `/health` remains an alias of `/health/live`.

## Frontend

- Server state lives in TanStack Query, one cache entry per resource: the
  library (meals, ingredient names, templates), one plan per week, one
  grocery list per week. Components never fetch.
- Mutations patch the cache from the API's response instead of refetching.
  When the server's effect is known (deleting a meal unassigns it from every
  week), the cache is corrected in place. A response is filed under the
  resource it names, not whatever is on screen when it arrives.
- Pending state is per area (`mealsPending`, `planPending`,
  `groceryPending`), never one flag that freezes the whole app.
- View state that should survive a refresh or a shared link (tab, week)
  lives in the URL, written with `replaceState` so the back button is not
  filled with every week visited. Unknown values fall back to a default.
- Types come from the generated API contract (see API above).
- The cache belongs to one account. Whenever the account on screen changes
  (log in, log out, a session ending mid-use) every query is reset and
  refetched; signing up is the exception, since a guest keeps their row.
- A `not-signed-in` answer starts a guest session (`api/client.ts`). Reads
  are then retried; writes are not, because replaying one would save it
  into a brand-new guest account. The person is told the change was not
  saved instead.
- Meal cards are `<article aria-label={name}>`, so tests and assistive tech
  find a meal by name rather than by text that may repeat.

Tests: `web/src/hooks/usePlanner.test.ts`, `web/src/hooks/useAccount.test.tsx`,
`web/src/App.test.tsx`, `web/src/api/client.test.ts`.

## Database

- Schema changes go through Alembic migrations only, reviewed by hand in
  both directions. CI applies every migration to an empty Postgres, runs
  `alembic check`, and downgrades to base.
- Production is migrated only by the `Migrate production` workflow, after
  approval, over Neon's direct connection rather than the pooler. Vercel
  deploys a push without waiting for it, so a migration must be safe for the
  code already running: additive changes are; anything else needs
  expand/migrate/contract (add, backfill and dual-write, then remove in a
  later release) or an agreed maintenance window.
- Dependencies update weekly through Dependabot, held back until a release
  is two weeks old.
- One transaction per request, opened in `server/deps.py`, and
  `Database.transaction()` is the only code that commits. Repositories are
  handed a session and never open, commit or roll back one; every write
  flushes before returning, so a constraint error comes from the method
  that caused it. Sessions have autobegin off, so a statement outside the
  transaction raises instead of opening a stray one. The dependency uses
  `Depends(..., scope="function")` so the commit happens before the
  response is sent: with the default scope a failed commit had already
  answered 200.
- Every table holding someone's data gets a row-level security policy for
  `meal_planner_app` in the migration that creates it, and explicit grants
  (no default privileges, so a new table is closed until a migration opens
  it). `tests/test_rls.py` fails if a table is neither under row security
  nor listed there as an auth table. Requests declare their user with
  `app.db.act_as`, called once, in `server/deps.py`. The web app connects
  as `meal_planner_app`; migrations and jobs connect as the owner.
- Owner-level work runs from two entry points and nowhere else:
  `python -m app.jobs <name>` (scheduled, `.github/workflows/jobs.yml`) and
  `python -m app.cli <command>` (by hand). Both connect as the owner, print
  the target first, and resolve the URL like migrations do, so a database
  not on this machine must be named in the shell. Jobs take the time as an
  argument and support `--dry-run`.
- Get-or-create is `INSERT ... ON CONFLICT DO NOTHING` then a lookup, never
  "look, then insert": two requests creating the same row at once both
  succeed instead of one hitting the unique index, which in Postgres also
  aborts the rest of its transaction.
- Queries are SQLAlchemy constructs, never string-built SQL.
- Reads that need related rows use explicit joins; there are no ORM
  relationships to lazy-load.
- Integer primary keys, and money as integer cents. Recipe quantities are
  floats because measurements are approximate.
- Plural snake_case table names (`meals`, `weekly_plans`).
- Every constraint is named by the metadata naming convention: `pk_<table>`,
  `fk_<table>_<column>_<referred table>`, `uq_<table>_...`, `ck_<table>_<rule>`,
  `ix_<table>_<column>`. A migration can then refer to any constraint by a
  name it can predict.
- Invariants live in the database as named constraints, not only in Python:
  names unique per user ignoring case (a unique index on
  `(user_id, lower(name))`), positive quantities and servings, weekdays only.
  A read-then-write check in Python races under concurrency; a constraint
  does not. Tests: `tests/test_schema_constraints.py`.
- Every foreign key states its `ON DELETE` (even `NO ACTION`) and is indexed,
  by its own index or as the leading column of another.
- Every table has `created_at` and `updated_at`, `timestamptz`, defaulted by
  the database so every writer gets them.
- Every query filters by its owner: repositories are constructed with a
  user and have no unscoped method. Lists have an explicit `ORDER BY`;
  without one the database may return rows in any order (an index added in
  the accounts migration made SQLite return meals alphabetically).
- SQLite enforces foreign keys (`PRAGMA foreign_keys=ON` on every
  connection), so local development behaves like Postgres.
- New migrations use a dated revision id and explain themselves:
  `alembic revision --rev-id 20261120_0001 -m "what changed"`, then a
  docstring saying what changes, why, and how the upgrade can fail.
  Migrations that move data are tested with data
  (`tests/test_migrations.py`), not only from an empty database.
- A database not on this machine is only migrated when named for that run:
  set in the shell (`MEAL_PLANNER_DB_URL='...'`, single-quoted, since Neon
  URLs contain `&`) or passed in by CI. A remote URL that `alembic` would
  pick up from `.env` is refused, a dev server never auto-migrates one, and
  every run logs its target first. Production changes go through the
  approval-gated `migrate` workflow; a branch rehearsal starts with
  `scripts/db_report.py` showing the branch's host.

Tests: `tests/test_conventions.py` walks every table and checks all of the
above. The schema itself is described in
[database-schema.md](database-schema.md).

## Tests

- The suite runs on SQLite and on Postgres in CI.
- When `TEST_DATABASE_URL` is set, the suite refuses to start unless the
  database name ends in `_test`, because it drops every table in it. The
  Postgres CI leg sets `REQUIRE_TEST_DATABASE=1`, so a missing URL fails
  instead of silently falling back to SQLite.
  Tests: `tests/test_database_safety.py`.
- Coverage floors are enforced in CI: 95% for Python, and per-metric floors
  for the frontend in `web/vitest.config.ts`. Raise them as coverage rises;
  never lower one to make a build pass.
- `pyright` type-checks `app/` and `server/`.
- Playwright runs the production build in Chromium against the real API on
  a fresh SQLite database (`npm run test:e2e`, and a CI job). Each spec works
  in its own week and names its own meals, so specs never depend on each
  other. Locate elements the way a user would (role and accessible name);
  if a control cannot be found that way, fix its accessible name rather than
  reaching for a CSS selector.
  Tests: `web/e2e/planner.spec.ts`.
